# 添加人字段需求说明

## 1. 背景与目标

当前阶段只有小王和小张两位固定使用者共同收集种草链接，但 v1 暂不做账号、登录、云同步、成员资料或权限系统。为了区分每条链接是谁添加的，需要在现有本地数据模型中增加一个轻量“添加人”属性。

目标是：

- 保存链接时能明确记录添加人。
- 整理为店铺、菜品后仍能看出来源是谁添加的。
- 用户可以按添加人筛选收件箱和想去内容。
- 不引入真实用户资料、登录态或协作权限。

## 2. 推荐方案

采用固定枚举字段 `addedBy`。

字段值：

- `xiaowang`：小王。
- `xiaozhang`：小张。
- `unknown`：未标记，仅用于历史数据迁移或异常兜底。

v1 只存储上述本地枚举值和固定显示文案，不存储手机号、头像、账号 ID、联系方式、登录凭证或权限信息。界面显示为“小王 / 小张 / 未标记”。如果后续人员发生变化，放到 v1.1 做“本地显示名称配置和人员变更迁移”，仍不等同账号系统。

## 3. 数据范围

### 必须新增

- `InboxItem.addedBy`：保存线索时写入，用于判断链接是谁添加的。
- `SourceLink.addedBy`：店铺可能有多个来源链接，每条来源都应保留自己的添加人。
- `Store.addedBy`：从线索整理为店铺时继承，用于卡片展示和筛选。
- `Dish.addedBy`：从线索整理为菜品时继承，用于卡片展示和筛选。

### 暂不新增

- `Plan.plannedBy`：谁安排计划是另一个语义，v1 先不做。
- `VisitRecord.recordedBy`：谁到店反馈也是另一个语义，v1 先不做。
- `Contributor` 独立对象：当前只有两位固定成员，不需要成员管理表。

## 4. 前端需求

### 收件箱保存

- 快速保存表单增加“添加人”选择控件。
- 控件使用二选一 segmented control 或等价按钮组，选项为“小王”“小张”。
- 新保存线索必须写入 `addedBy`；如果没有值，前端应阻止保存并提示选择添加人。
- 为保持保存路径轻量，可以默认选中上一次选择；如果没有历史选择，默认 `xiaowang`。
- 手动补充标题、店名或菜名的逻辑保持不变。

### 收件箱展示与整理

- 收件箱卡片展示添加人 chip。
- 快速整理为店铺、菜品、店铺 + 菜品时，默认继承 `InboxItem.addedBy`。
- 暂留线索不改变 `addedBy`。
- 重新解析只更新链接元信息，不覆盖 `addedBy`。
- 合并来源到已有店铺时，新 `SourceLink` 保留该线索的 `addedBy`；已有店铺本体的 `addedBy` 不自动覆盖。

### 想去列表与筛选

- 店铺/菜品卡片展示添加人 chip。
- 筛选区增加“添加人”筛选：全部、小王、小张、未标记。
- 添加人筛选应和搜索、标签筛选叠加生效。
- 搜索关键字不需要默认命中“小王/小张”，避免把身份筛选混进普通文本搜索。

### 编辑能力

- 店铺编辑表单允许修正 `addedBy`。
- 菜品编辑表单允许修正 `addedBy`。
- v1 可以不提供批量修改添加人。

### 我的页

- 数据版本信息中可以说明当前支持固定两位添加人。
- v1 不提供成员管理入口。

## 5. 数据层与轻后端需求

### 领域层

- `createInboxItem` 接收 `addedBy`，新数据必须校验为 `xiaowang` 或 `xiaozhang`。
- `organizeInboxItem` 创建 `Store`、`Dish`、`SourceLink` 时继承线索的 `addedBy`。
- `mergeInboxItemIntoStore` 合并来源时，新增来源链接继承线索的 `addedBy`。
- `addSourceLink` 支持传入 `addedBy`；如果来自手动新增来源，默认使用当前选择的添加人。
- `updateStore` 和 `updateDish` 支持更新 `addedBy`。
- 新增筛选函数或扩展现有筛选逻辑，支持按添加人过滤店铺、菜品和收件箱。

### 存储与迁移

- `DATA_VERSION` 需要升级。
- `migrateState` 对旧数据补齐：
  - 缺失 `InboxItem.addedBy` 时设为 `unknown`。
  - 缺失 `Store.addedBy` 时设为 `unknown`。
  - 缺失 `Dish.addedBy` 时设为 `unknown`。
  - 缺失 `SourceLink.addedBy` 时设为其所属店铺的 `addedBy`；如果店铺也缺失，则设为 `unknown`。
- 迁移不得删除或覆盖旧收藏、计划、轻反馈、标签和来源链接。

### `/api/link-preview`

- 链接预览接口不需要接收或返回 `addedBy`。
- 添加人属于前端本地收藏数据，不进入后端解析逻辑。
- 后端仍不保存用户收藏数据或添加人字段。

## 6. 非目标

v1 不做以下能力：

- 登录、账号、成员邀请。
- 云端用户 ID。
- 权限控制。
- 手机号、头像、账号 ID、联系方式等用户资料。
- 谁计划、谁到店、谁反馈的独立记录。
- 多人协作消息流。
- 按添加人统计贡献度或排名。

## 7. 验收标准

- 新保存一条收件箱线索时，数据中必须包含 `addedBy`。
- 未选择添加人时不能保存新线索。
- 从收件箱整理为店铺、菜品、店铺 + 菜品后，新对象和来源链接必须继承原线索的 `addedBy`。
- 收件箱卡片、店铺卡片、菜品卡片能看到添加人。
- 想去列表可以按添加人筛选，并且能与标签筛选、搜索同时生效。
- 历史数据迁移后不丢数据，缺失添加人的旧记录显示为“未标记”。
- 重新解析链接不会改变添加人。
- 合并来源到已有店铺时，新来源链接保留自己的添加人，已有店铺不会被静默改归属。

## 8. 测试建议

- 领域层测试：
  - `createInboxItem` 校验合法/非法 `addedBy`。
  - `organizeInboxItem` 继承 `addedBy`。
  - `mergeInboxItemIntoStore` 继承来源链接 `addedBy`，不覆盖店铺本体。
  - `migrateState` 为旧数据补齐 `unknown`。
  - 添加人筛选和标签筛选叠加生效。
- UI 测试：
  - 快速保存表单展示添加人控件。
  - 保存后收件箱卡片展示添加人。
  - 整理后想去卡片展示添加人。
  - 添加人筛选能隐藏/展示正确卡片。

## 9. 默认假设

- 两位成员在 v1 中固定存在，不需要增删成员。
- 默认显示名称为“小王 / 小张”。
- 历史数据使用“未标记”，不强制一次性补录。
- 添加人只代表“谁添加了这条线索或来源”，不代表“谁想去”“谁安排”“谁实际去了”。
